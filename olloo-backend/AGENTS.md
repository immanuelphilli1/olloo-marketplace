# AGENTS.md - HandCO API

Laravel 12 ecommerce API (`/api/v1`, Sanctum bearer) + Inertia React staff admin under an obscured prefix. Vite alias `@` maps to `resources/js`.

## Commands

```bash
composer dev            # serve + queue:listen + pail + vite (concurrently)
php artisan test        # full suite (sqlite :memory:, currency rows provider=fake)
php artisan test --filter=TestName   # single test/class
./vendor/bin/pint       # PHP formatter
npm run build           # admin frontend build (vite + tailwind v4 + React 19)
php artisan migrate --seed            # local setup needs seeded currencies/categories/users
php artisan route:list  # verify named routes before wiring frontend links
```

`composer test` runs `config:clear` then `artisan test`. No CI workflows in repo; run `pint` + focused test before finishing.

## Client-facing rids only (never numeric ids)

- Public models use `HasRid` (`app/Models/Concerns/HasRid.php`); route key is `rid`, auto-generated by `generate_rid()`.
- API JSON and Inertia props emit `rid` (numeric `id` is `$hidden`). Frontend spec names like `productId`, `addressId`, `orderId` are **rid strings**.
- Guest cart identity is the cart **rid** in `X-Cart-Id` header/cookie; merge it on login via `POST /api/v1/cart/merge`.
- Internal FKs stay numeric (`*_id`); only the wire format is rid-only.
- Postman examples/variables are rids only (`postman/`).

## API conventions

- Errors via `api_error($code, $message, $status, $details)` (`app/Support/helpers.php`): `{ "error": { "code", "message", "details?" } }`. Validation/401/404 are normalized in `bootstrap/app.php`; reuse `api_error` via `abort(api_error(...))` instead of inventing shapes.
- Lists: `{ items, total, page, limit }`. Money: `money($minor, $code)` returns `{ amount, currency }` (decimal by default). Prices are stored as `*_minor` ints.
- Always use named routes over raw URLs; name new routes when defining them. API base is `/api/v1`; webhooks are top-level `POST /webhooks/{provider}` (not under `/api/v1`).

## Payments (Stripe + Paystack behind a port)

- `app/Payments/`: `PaymentGatewayManager`, `CurrencyGatewayResolver`, `Gateways/*`, `Contracts/`, `DTOs/`.
- There is no default provider config. Routing is per currency: `currencies.payment_provider` (`CurrencyGatewayResolver::forCurrency`) unless the shopper picked a `payment_methods` row, whose `provider` wins. Blank/unknown provider must throw loudly; never fall back to Stripe or any other gateway, and `PaymentGatewayManager::gateway()` requires an explicit key. The currency seeder pins USD and AED to `stripe` and GHS to `paystack` (one gateway per market; a mismatch fails at the gateway, e.g. Paystack's "No active channel to process transaction"). `fake` is only for local/test: `FakeGateway` throws in production and its `verifyCharge` reports the stored payment's amount/currency, so settlement amount checks run in tests.
- Webhooks (`routes/webhooks.php`, outside Sanctum/session auth): resolve by payment rid or provider reference in payload, `verifyCharge` before marking paid, persist idempotently by `(provider, external_event_id)`. Never read `X-Cart-Id`, bearer tokens, or staff session in a webhook.
- Gateway returns land on `/checkout/return/{provider}` and `/checkout/cancel/{provider}` (`routes/web.php`, public, `CheckoutReturnController`), one path per provider matching `payments.providers.*.return_url`/`cancel_return_url`. We own this hop: resolve the payment by the reference we appended (scoped to that provider, so one gateway's return never exposes another's payment), re-verify with the provider, then 302 to `services.storefront.url` + `return_path`/`cancel_path`. A provider outage still redirects with the stored status rather than stranding the shopper. The redirect target is always the configured storefront plus a fixed value set, never query-string input, so it cannot become an open redirect; an unresolved reference is dropped rather than echoed. `WEB_CLIENT_URL` must be absolute or the redirect fails loudly.
- Order first, then pay: `POST /orders` creates `status=pending_payment`, `payment_status=unpaid` with frozen totals and held stock; `POST /checkout/payment-intent {orderId}` charges exactly `orders.total_minor`. Settlement (`PaymentSettlementService`) only marks an order paid when amount/currency match and the order is still payable; otherwise the payment becomes `needs_review`. Never reintroduce cart-total payments or payment-less orders.
- Order `status` (fulfilment, `OrderStatus` enum) and `payment_status` (`OrderPaymentStatus`) are separate; staff cannot ship/deliver unpaid orders. Cancelling goes through `OrderService::cancel` so stock is released.
- `POST /orders` and payment-intent require `Idempotency-Key` (`idempotent` middleware, `idempotency_keys` table). Add it to any new endpoint that creates money-moving records.
- There is no `CountryGatewayResolver`. Three things resolve a country and they are not interchangeable: `ShopperLocale::country()` picks the shopper's market (and so the currency), `DeliveryDestination::fromRequest()` picks the shipping/tax destination, and `PaymentMethodResolver` filters methods by the market. All read `?country=` except where noted. `CheckoutController::previewDestination()` uses `DeliveryDestination::forUser()` and ignores `?country=` on purpose, so a Dubai shopper shipping to Accra is quoted Accra freight in GHS; `CheckoutController::shopperMarket()` uses `ShopperLocale::country()` for the method list, because a method's country list is about where it is offered, not where the parcel goes. Feeding the destination into the method filter is what emptied the list for cross-border shoppers.
- `PaymentMethodResolver::available(string $currency, ?string $country)` takes currency as required, not optional. A currency always resolves, so a null here only means a caller forgot, and returning every active method would show options the order cannot pay with. The country is the shopper's **market** (`ShopperLocale::country()`), never the delivery destination: a card pays an order shipping to another country perfectly well, and filtering on `DeliveryDestination::forUser()` is what emptied the list for anyone crossing a market border. `GET /payment-methods/checkout` resolves both params itself when omitted and 422s on an unresolvable `country` rather than treating it as "market unknown", which would widen the list on a typo.
- Two passes over the same gate. First the rows scoped to the market (`is_fallback = false`), then, **only if that is empty**, the `is_fallback` rows, which the seeder puts on the store default currency's methods (USD, `countries: []`). So an unconfigured market still gets a way to pay instead of a dead end, and a configured one never sees the extras. `supports()` still applies to a fallback, so a GHS cart cannot land on a Stripe row: the USD rows do not list GHS, and that is the "No active channel to process transaction" failure. `available()` and `resolve()` must run the same check, or the preview offers a method the payment call refuses.
- The scheduler must run (`* * * * * php artisan schedule:run`): `orders:expire-unpaid` cancels unpaid orders after `PAYMENTS_ORDER_PAYMENT_WINDOW_MINUTES` and releases stock; `model:prune` clears old idempotency keys.

## Catalog and money invariants

- Variants are the sellable unit: every product has one `is_default` variant; each has a unique `sku` and `stock_quantity` (NULL = not tracked). Cart lines always reference a variant.
- Cart lines price at the variant's current price; `cart_items.unit_price_minor` is the price the shopper last saw. Orders refuse to place (`409 price_changed`) until they match.
- Currency comes from `Currency::defaultCode()` (the `is_default` row) and throws when missing. USD is the default and the catalogue is priced in it; AED and GHS are local markets. No `'USD'` fallbacks in code or DB defaults.
- Attributes are defined per category (`category_attributes`: stable `key`, `label`, optional `options`) and inherited by subcategories; products only set values for attributes their category lineage offers (`Category::availableAttributes()`, enforced in `Product::syncAttributes`). Facet data lives in `product_attributes`; storefront presentation hints live in `products.display` JSON. Shipping cost and delivery time come only from shipping rules (fee, `transit_days_min/max`, optional shipping class) plus variant `handling_days` (NULL = `SHIPPING_DEFAULT_HANDLING_DAYS`). Carts are quoted per shipping class and summed. Storefront delivery claims (`delivery`, `deliveryQuote`, free badge) appear only for a known destination (`?country=` or the customer's default address) and read `product_delivery_quotes`, refreshed by model events and `php artisan delivery:refresh` (run it after deploys that touch shipping).
- Users soft-delete (`DELETE /users/me`); `active_email` (generated) keeps email unique among live accounts, so email uniqueness rules must use `->withoutTrashed()`. Orders and products use `restrictOnDelete` FKs.

## Shopper currency (`app/Currency/`)

- `ShopperLocale` decides the country and the currency. Country order: `?country=`, then the user's `preferred_country`, then `assigned_country`, then live IP via `GeoIpCountry`, then the default currency's own `currencies.country_code` (`countrySource` reports which). The two country settings live in `user_settings` (`UserSetting::PREFERRED_COUNTRY` / `ASSIGNED_COUNTRY`, stored as ISO codes, read only for the sanctum user). `assigned_country` is written once from the first detected IP via `putIfAbsent` and never re-detected, so a traveller's currency holds; a shopper overrides it with `PUT /users/me/country` (`preferredCountry`, `null` clears), which calls `ShopperLocale::forget()` because the answer is memoised per request. The last fallback is `currencies.country_code`, never derived by inverting `countries.currency_code`: that column is many-to-one (18 countries carry USD) and the alphabetical pick resolved to American Samoa. A currency with no `country_code` logs a warning and answers null rather than throwing, because 500-ing every storefront page over a missing code is worse than the null. Currency: the country's `currency_code` only when it is a `currencies` row with a fresh rate from the default; otherwise `Currency::defaultCode()`. Never show or charge an unsupported currency. `GET /api/v1/locale` exposes the locale as `ShopperLocale::toArray()`.
- `CurrencyConverter` converts minor units at mid rate x (1 + markup%), rounding up. Markup: `currency_conversions.markup_percent` per pair, else the admin default (`MarkupSettings`, `app_settings`). A missing or older than `CURRENCY_MAX_RATE_AGE_HOURS` (36) rate throws `ExchangeRateUnavailable` (API 503 `exchange_rate_unavailable`); never fall back to a guessed rate.
- Prices stay stored in the product's currency. `cart_items.unit_price_minor` is in the product currency, so rate refreshes never trip `price_changed`; carts follow the shopper's currency (`CartService::resolveCart`). Convert at the edge (`CartItem::unitPriceMinorIn`, `ProductMapper`), never in storage.
- Orders freeze converted prices and record `order_items.source_*`, `orders.base_total_minor` (mid rate, no markup) and `fx_snapshot` (rates used). Keep the snapshot when touching order placement.
- `currency:update-rates` runs twice daily (exchangerate-api.com, keyless open.er-api.com without `EXCHANGE_RATE_API_KEY`). IP lookups are cached per IP (misses too) with a provider backoff; behind a proxy set `TRUSTED_PROXIES` or every visitor looks like the proxy.
- Shipping rules in the quote currency win; rules in other currencies are converted (threshold and fee). `money()` uses the currency's `decimal_places`.

## Admin (Inertia, session guard `staff`)

- Routes in `routes/admin.php`, mounted at `config('admin.path_prefix')` (`ADMIN_PATH_PREFIX`, default obscured). Auth chain: `auth:staff` -> `staff.password` (force reset) -> `staff.mfa` (`ADMIN_MFA_FORCED=true`).
- Customers and staff share the `users` table; staff login is the separate `staff` session guard, not Sanctum.
- `user_type = staff` grants admin access on top of shopping, not instead of it: one account, one email and one password sign in to both the shop (Sanctum) and the admin (`staff` guard, with MFA). Never filter shop auth (`login`, `check-email`, Google OAuth) by `user_type`. The admin Customers list includes staff who have orders. `POST staff` with `customer` (a customer rid) promotes that account and keeps its password unless staff set a new one.
- Storefront banners are `inhouse_placements` (admin **Banners**, `GET /api/v1/placements/{page}`). Slots (page + position) are fixed in `InhousePlacement::SLOTS` and validated with `in:`, never free text, because each slot is a storefront component; add a slot together with its component. Today: `home.hero` (`HeroSection`), `home.promo` (`PromoBannerSection`) and `site.nav_video` (the video strip in `Nav`, every page). Video slots are listed in `InhousePlacement::VIDEO_SLOTS`: `video` holds the clip (uploaded through `admin.uploads.video`, MP4/WebM, typed by content), `image` is the required poster, and title/description/button are cleared.
- Admin **Export CSV** (Products list, with its filters; Categories). The product file uses `ProductCsvImporter::COLUMNS` exactly (one row per variant, default first, store link repeated, category by slug), so an exported file re-imports with no changes; `CatalogExportTest` holds that round trip, so change the export and the import together. `CsvExport::cell` prefixes cells that would run as spreadsheet formulas (`= + - @`) with `'`, and the importer strips it.
- Login/logout must return `Inertia::location(...)`, not `redirect()`, or `window.Ziggy` stays guest-filtered and `route('admin.*')` breaks (skill `admin-auth-ziggy-reload`).
- Demo seed logins: `demo@handco.test` (customer), `jaygrey.jg@gmail.com` (customer), `admin@handco.test` (staff), password `password`.

## Observability / notifications

- Log every outbound call (mail, Stripe, Paystack, geo, etc.) via `ExternalRequestLogger::logOutgoing`/`fromHttp` in a `finally` so failures are recorded too. Mail success comes from `MessageSent`, queued failure only from `JobExceptionOccurred` on `SendQueuedMailable`; `MessageSent`-only logging hides SMTP errors.
- Staff alerts go only to admin-configured recipient emails matched case-insensitively to staff accounts (`StaffNotificationFanout::notifyStaffEmails`). Empty recipient list means nobody; never fan out to all staff.

## Frontend (admin `resources/js`)

- Every clickable (`button`, `onClick` targets, chips, tabs) needs `cursor-pointer`; disabled uses `cursor-not-allowed`.
- Create/edit forms: sections before steps, never tabs-as-wizard; three-level validation (field error + section marker + top summary), inputs preserved. No shared UI kit: inline Tailwind, shared bits in `@/Components`. Details: `.claude/rules/admin-frontend.md`.

## Migrations / seeders

- Never rename a migration file once any env may have run it (history is by filename; rename causes `Table already exists` on deploy). Make creates idempotent instead.
- Tests run on sqlite, production on MySQL: index/foreign-key changes that pass on sqlite can fail on MySQL. Verify alter migrations against a scratch MySQL database (skill `mysql-safe-migrations`).
- `DatabaseSeeder` order matters: permissions -> currencies -> categories -> products -> geo -> content -> users -> sample orders. Keep model events enabled so `HasRid` fills `rid`.
- **Every deploy** runs `php artisan db:seed --class=ProductionDatabaseSeeder --force` after `migrate`. Never `php artisan db:seed` in production: that is `DatabaseSeeder` and it creates demo accounts, products and orders.
- `ProductionDatabaseSeeder` holds only seeders that are safe to re-run on a live database: `AdminPermissionsSeeder`, `CurrencySeeder`, `GeoSeeder`, `PaymentMethodSeeder`. Two tests in `tests/Feature/ProductionDatabaseSeederTest.php` hold the membership (each excluded seeder has a test naming the staff work it would revert) and idempotency, so adding a seeder to it means answering both.
- A deploy seeder must never overwrite a field the admin portal lets staff change. `ShippingRuleSeeder` (fees), `TaxSeeder` (rates) and `CategorySeeder` (`is_active`) all do, so they are excluded. `CurrencySeeder` writes `payment_provider` and `is_default` only on new rows, because `PaymentMethodController::updateCurrency` exposes both.

## Docker and deploys

- **The deploy job runs on a self-hosted runner on the production host** (`runs-on: [self-hosted, Linux, ARM64]`, the host being `aarch64`). It builds the image there and switches it live, so there is no registry and no SSH back into the machine. The **test job stays on GitHub-hosted runners**: the suite and the frontend build must not share CPU with shoppers. `docker/scripts/install-runner.sh` sets the runner up (creates `handco-deploy`, adds it to the `docker` group, downloads the runner matching `aarch64`, grants narrow NOPASSWD sudo for the proxy reload and the release `mkdir`/`cp`/`chmod`). **The runner's labels must equal the job's `runs-on` set** — a mismatch leaves the runner idle and the job queued forever with no error, which is the most common way this goes wrong. A docker-enabled runner is root on that box: restrict it to the `deploy` branch, keep it a repository runner, and keep the `production` environment approval. Every base image is multi-arch, so ARM64 needs no per-arch branch in the Dockerfile; if the host moves to x86, `runs-on` has to change with it.
- **The build competes with live traffic.** Composer and Vite run on the same CPUs and RAM as the shop. The deploy workflow prints `/up` latency before the build and after the switch so the cost is visible. Mitigations in order: size the host, keep the Docker layer cache (only `composer.lock`/`package-lock.json`/`COPY . .` change between deploys), `NODE_OPTIONS=--max-old-space-size=4096` already caps the Vite heap, and deploy off-peak. If `/up` during the build is bad on the real host, the box is undersized and the answer is a separate builder plus a registry, not a bigger timeout.
- **Unresolved: `/up` intermittently takes ~3.1s** (about 1 request in 8, at rest, unrelated to deploys, and it still happens at host load 0.92 so it is not CPU). Ruled out: config/route cache, `pm.max_children`, the queue worker, opcache `validate_timestamps`, port publishing, DNS for the `app` upstream (0ms), TCP connect to php-fpm (0ms), framework boot (stable 420ms in CLI). Only the FastCGI path is affected; static files are 3ms. A php-fpm `slowlog` at 2s produced **no** trace, which points at nginx's own upstream handling rather than PHP. Next step: log `$upstream_connect_time` / `$upstream_header_time` / `$upstream_response_time` in the gateway. Full table in `docs/DEPLOYING.md`. Do not paper over it with a bigger timeout.
- MySQL is **not** in Docker. It stays on the host; containers reach it over `host.docker.internal`, which needs `docker/scripts/expose-host-mysql-to-docker.sh` once per host (DNATs docker0 to 127.0.0.1:3306, raises `max_connect_errors`, flushes the host cache, and survives reboot via a systemd unit). `DB_CONNECTION` other than `sqlite` makes the entrypoint wait for it, and it waits with a real `mysqladmin ping`, never a bare TCP probe.
- `docker/Dockerfile` targets: `production` (php-fpm, for app/queue/scheduler), `gateway` (nginx, `public/` copied from production so both tiers serve one build), `development`, `gateway-dev`. Build from `docker/compose.yaml` alone; `docker/compose.prod.yaml` sets `build: !reset null` on every service because the server only runs images CI built. `!reset` needs Compose 2.24+; plain `build: null` does not clear an inherited key.
- Uploaded images (`Storage::disk('public')`, `/storage/...`) are served by the **gateway**, not php-fpm. The gateway mounts `storage_data` read-only and serves `/storage/` with `alias /var/www/html/storage/app/public/`. Never rely on the `public/storage` symlink there: the entrypoint creates it inside the app container only, and with `root` + the symlink every product, category and banner image 404'd in production while `/up` passed. CI check 7 in the production gateway step guards this.
- **Storefront SEO pages go through Laravel.** The gateway sends `/`, `/categories`, `/categories/*` and `/products/*` to `StorefrontPageController` (`routes/storefront.php`, no web middleware, so no session or DB is needed for `/`). It reads the published `index.html` from the **app** container's read-only mount of the web root (`compose.prod.yaml`) and injects title, description, canonical, Open Graph and JSON-LD from `StorefrontSeo`; `GET /api/v1/seo?path=` returns the same answer for client-side navigation. Those locations use `fastcgi_intercept_errors` + `error_page 5xx = @spa_shell`, so a PHP failure serves the plain SPA instead of an error. `/sitemap.xml` and `/robots.txt` are Laravel too; never put the admin prefix in robots.txt. CI check 8 proves the app can read the mount. Canonical URLs need an absolute `WEB_CLIENT_URL`.
- **Product pages are server-rendered by the storefront's Node SSR server** (`handco-ssr`, host network, `127.0.0.1:8041`, deployed by the storefront repo's workflow). Production's host proxy is **Apache**, and `release.sh` writes the routing into `proxy.conf`: `/products/*` goes to `balancer://storefront-ssr` with the release's own gateway as hot standby (`status=+H`), so a dead or restarting SSR server fails over to the Laravel head injection in the same request. The SSR server calls the API through Apache's internal listener `127.0.0.1:8039` (`/api/` only), which copies its `X-Forwarded-For` into `CF-Connecting-IP`; the public vhost sets `CF-Connecting-IP` from `REMOTE_ADDR`, because production is not behind Cloudflare and the gateway reads the client address from that header only. The gateway must pass PHP `REMOTE_ADDR $realip_remote_addr` (the proxy) and the visitor in `X-Forwarded-For`: passing the real_ip-resolved visitor as `REMOTE_ADDR` made Laravel distrust the proxy and serve the admin's assets over `http://` (mixed content). Needs `a2enmod proxy_balancer lbmethod_byrequests slotmem_shm headers remoteip`. `publish-web.sh` carries the previous build's entry bundles into each release. Full runbook: `docs/DEPLOYING.md` 3b.
- php-fpm pool settings live in `www.conf` via a Dockerfile `sed`, **not** in `docker/php/php.ini`: php-fpm ignores a `[www]` section in `conf.d`, so a block there looks correct and does nothing. `pm.max_children` is 16 against the stock 5; size it against the container's memory limit, not the host's.
- Deploys are blue/green, because Compose cannot republish a bound port and recreating in place means the old container stops first. Two releases run side by side under different project names on 8031/8032. `docker/scripts/release.sh` migrates, starts the new stack, health checks it on its own port, writes the upstream file, repoints `current` with `ln -sfn` plus `mv -Tf`, reloads the host proxy, verifies through `PUBLIC_URL`, and only then stops the old stack. The `current` symlink is the cut-over because the host nginx includes `current/upstream.conf`.
- Never put a directive the host proxy already has into `upstream.conf` (only `server 127.0.0.1:PORT`); a repeated `keepalive` is a nginx "duplicate directive" fatal that takes the proxy down on reload. The proxy runs on the **host**: `127.0.0.1` inside a container is that container, not the published port.
- `release.sh` is the rollback tool too (`sudo release.sh <release-dir>`), so rollback is not a second implementation. Each release holds its own merged `docker/env/app.env`, so a rollback restores the settings it was verified with. `HOST_PROXY` accepts `nginx`, `apache`, `none`, or any reload command.
- `.github/workflows/ci.yml` runs on every push and PR on GitHub-hosted runners; `deploy.yml` calls it via `uses:` and its deploy job runs on the self-hosted production runner on a push to `deploy`, so merging is not deploying. CI cannot test the host-MySQL bridge (it depends on docker0 and the target's mysqld), so it proves the images instead: build, boot, migrate on sqlite, hit `/up` and `/api/v1/locale`. Verify the MySQL bridge by hand during server setup.
- Docs: `docs/DOCKER.md` (local, services, entrypoint, database trouble), `docs/DEPLOYING.md` (server setup, first deploy, zero-downtime mechanism, rollback, and what the rehearsal measured), `docker/PORTS.md` (port map and conflicts).

## Env

`env()` belongs in `config/` and nowhere else. Under `php artisan config:cache` Laravel never loads `.env`, so `env()` outside a config file silently returns its default instead of failing. Always read `config('...')`, including in migrations (`NoEnvOutsideConfigTest` enforces this). Config keys wrap the value: `(int)`, `(bool)`, `(string)`, or a `??` fallback for nullable ones.

`EXCHANGE_RATE_API_KEY` (optional, `currency:update-rates`), `IPINFO_TOKEN` (IP country detection; blank disables it), `TRUSTED_PROXIES`, `CURRENCY_MAX_RATE_AGE_HOURS`, `CURRENCY_DEFAULT_MARKUP_PERCENT` (until staff save one), `RESTCOUNTRIES_API_KEY` (`php artisan countries:sync` and the admin Countries page sync; never deletes rows), `CORS_ALLOWED_ORIGINS`, `WEB_CLIENT_URL` (absolute storefront base that gateway returns bounce to), per-provider `<PROVIDER>_RETURN_URL`/`<PROVIDER>_CANCEL_RETURN_URL` (`STRIPE_*`, `PAYSTACK_*`, `PAYPAL_*`, `TABBY_*`, `TAMARA_*`; paths resolve against `APP_URL`, gateways reject a relative redirect URL, and each gateway has its own page like the Google OAuth redirect), `ADMIN_PATH_PREFIX`, `ADMIN_MFA_FORCED`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_OAUTH_REDIRECT_URL` (web client callback page; API exchanges the code). Tests force sqlite `:memory:`, `MAIL_MAILER=array`, `QUEUE_CONNECTION=sync` via `phpunit.xml`.
